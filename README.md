                                 Invoice Management System — Backend API (Laravel 13)

Реалізація бекенд-частини full-stack системи автоматизації роботи бухгалтерів для обліку рахунків (invoices).

Інструкція із запуску проєкту (Docker)

Для запуску розробницького середовища переконайтеся, що на вашому комп'ютері запущено додаток Docker Desktop.

1. Налаштування оточення

Скопіюйте файл конфігурації зміних оточення:

cp .env.example .env

Переконайтеся, що у файлі `.env` налаштовано правильні доступи до бази даних MySQL, як описано в інструкції розробника.

2. Збірка та старт контейнерів

Запустіть процес збірки та старту локальних сервісів (PHP 8.2+ та MySQL 8.0) у фоновому режимі:

docker-compose up -d --build

3. Налаштування бази даних

Запустіть міграції для створення структури таблиці інвойсів всередині Docker-контейнера:

docker-compose exec backend php artisan migrate

Проєкт буде успішно запущений і доступний за адресою: http://localhost:8000

Інтерактивна API Документація (Swagger)

У проєкт інтегровано пакет L5-Swagger (OpenAPI 3.0), який автоматично документує всі ендпоінти, структури запитів та
відповідей на основі строгих PHP-атрибутів.

Swagger UI доступний за посиланням: http://localhost:8000/api/documentation

Тут ви можете наочно протестувати роботу методів `GET`, `POST` та `PUT` безпосередньо з браузера.

Відповіді на архітектурні питання з ТЗ

1. Як ти структурував frontend і backend?

Проєкт побудовано за архітектурою Separated Repositories / Folders для повної незалежності клієнтської та серверної
частин.

Бекенд структуровано за стандартами чистої архітектури та Best Practices фреймворку Laravel:

- Controllers: Максимально «тонкі» контролери (`InvoiceController`), які відповідають лише за прийом запиту та
  повернення стандартизованих JSON-відповідей через `JsonResource`.
- Form Requests: Винесено шар вхідної валідації (`StoreInvoiceRequest`, `UpdateInvoiceRequest`).
- Custom Rules: Складна бізнес-валідація фінансів та дат інкапсульована в окремі класи правил (`MatchGrossAmount`,
  `ValidDueDate`), що розвантажує реквести та забезпечує повторне використання коду (DRY).
- Services: Уся бізнес-логіка (взаємодія з базою даних, збереження, оновлення) ізольована у сервісному шарі (
  `InvoiceService`).

2. Які компроміси ти зробив і чому?

- Відмова від автентифікації: Згідно з приміткою у ТЗ (Аутентифікація не потрібна), пакет `Laravel Sanctum` або
  JWT не налаштовувалися для прискорення розробки та спрощення інтеграції з фронтендом.
- Використання UUID замість Auto-increment: Для первинних ключів (`id`) обрано UUID. Це створює незначне додаткове
  навантаження на індекси, але повністю унеможливлює перебір ID зловмисниками (безпека) та значно полегшує генерацію
  об'єктів на стороні фронтенду без ризику збігу ідентифікаторів.

3. Що б ти покращив у production-версії?

- Database Transactions (`DB::transaction`): Загорнув би методи створення та оновлення в транзакції бази даних, щоб
  у разі системного збою дані не залишалися в розсинхронізованому стані.
- Версіонування API: Перейшов би на префікси маршрутів (наприклад, `/api/v1/invoices`), щоб подальші оновлення
  бекенду не зламали поточну версію фронтенду.
- Автоматизоване тестування: Покрив би сервіси та правила валідації Feature та Unit-тестами за допомогою
  PHPUnit.

4. Які UX edge cases ти врахував?

- Похибка обчислень Float чисел: Фінансова перевірка рівності математики (`gross_amount = net_amount + vat_amount`)
  реалізована через дельту в 1 цент за допомогою функції `abs()`. Це запобігає збоям валідації через специфіку
  округлення двійкових дробів процесором (наприклад, коли `0.1 + 0.2` перетворюється на `0.30000000000000004`).
- Захист від маніпуляцій з датами*: При оновленні інвойсу (`PUT`) нове поле `due_date` валідується відносно
  оригінальної дати виписки (`issue_date`), яка вже надійно збережена в базі даних (навіть якщо фронтенд не надсилав
  поле `issue_date` у поточному запиті).
- Блокування модифікації закритих документів (403 Forbidden): Метод авторизації реквесту жорстко перевіряє статус
  інвойсу безпосередньо в базі даних. Якщо статус відмінний від `pending` (наприклад, `approved` або `rejected`), сервер
  миттєво відхилить `PUT` запит, навіть якщо користувач спробує обійти заблокований інтерфейс фронтенду через Postman чи
  cURL.
